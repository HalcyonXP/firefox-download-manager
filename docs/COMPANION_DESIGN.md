# Visible companion implementation — #50

Status: implementation in progress; not an installable successor release. This branch starts from main f944247 independently of #49/PR55. Provider feasibility observations and browser/signing/handoff proof remain separate in #49/PR55. Component checks do not establish installed workflow acceptance.

## Boundaries selected before implementation

- **Engine owner**: one Rust owner retains the existing TaskEngine state lock, settings and task lifetimes. Browser transport EOF is a client disconnect, not companion Quit. Legacy on-demand run_host retains EOF shutdown independently of the paired application bridge; do not silently detach the released host.
- **Visible shell**: Windows-native status window, tray icon, Open/status and deliberate Quit. First increment is an explicitly marked preview in an exclusively created temporary domain, never the installed state root. It does not pretend the Firefox bridge exists.
- **Visibility gate**: engine startup follows successful tray registration and confirmation. Failed registration leaves a visible error and no engine. Window close can hide only while the tray is confirmed. Quit requests cooperative engine shutdown, joins the retained worker, then removes the icon and exits. A failed shutdown must remain visible rather than report success.
- **Shell recovery**: confirm registration on an owned-window timer; re-add only this app's icon if confirmation fails. If re-add fails, show the status window. This is timer-driven recovery, not immediate TaskbarCreated notification or a guarantee against OS scheduling stalls. Test loss of the owned icon, not termination of Explorer. Windows tray overflow is not absence of registration.
- **IPC direction (transport foundation below; installed bridge still pending)**: bounded local Windows named pipes, explicit current-user ACL and remote-client refusal, random per-generation/session capability, paired bridge/companion version, independently checked generation authority, bounded clients/queues/deadlines and deterministic refusal of unknown installations. No HTTP listener or URL/secrets in process arguments. Current-user confinement does not defend against administrator or arbitrary code already running as that user. Credentials and sensitive URLs must stay out of ordinary logs.
- **Protocol direction**: v2 manual task controls remain the compatibility baseline; automatic handoff needs a separately versioned prepared/committed intent contract established with #49/#51. A lost Add acknowledgement must not trigger an automatic replay. No browser profile or registered host is repointed to a partial implementation.
- **Setup migration direction**: a future paired package adds the companion and an ordinary setup UI/owned shortcut, migrates only verified receipts/generations, closes both Firefox editions normally before registration changes and preserves downloads/task state/unknown files. Existing generation manifests are not edited in place. Preview bytes are excluded from the current package payload list; no v0.1.0 tag/asset is replaced.

## Dependency choice and rejected shortcuts

winsafe0.0.29 is selected for safe native-window and Shell_NotifyIcon wrappers, features gui/shell only, no default features, no transitive dependencies or build script. Its full MIT license, package manifest and relevant API wrappers were reviewed before incorporation. At the initial shell checkpoint first-party unsafe_code remained forbidden. [ADR0015](decisions/0015-owned-windows-io-cancellation.md) now adds one explicit function-local cancellation exception in a separate Windows I/O boundary; the shell and all existing crates retain forbid. No third-party implementation source is copied.

A direct TaskbarCreated handler through winsafe would require unsafe conversion from its registered u32 message ID to its typed WM; this was not used or bypassed. The chosen adapter instead uses the predefined WM_APP for its owned icon callback and a timer for confirmation/re-registration. No raw Win32 FFI is needed for those UI operations; no Windows message-filter/protection change is made. The separate IPC cancellation boundary is addressed by ADR0015.

tray-icon0.24.2 was reviewed but not selected: its constructor can retain a window after failed icon registration (build success alone is not visibility), and the selected design does not need its extra menu/platform dependency tree or message-filter adjustments. native-windows-gui1.0.13 was considered but not selected. interprocess2.4.4 was initially only an IPC candidate. The subsequent [local transport increment](LOCAL_IPC.md) selects its server/security-descriptor APIs, not its client constructor or default flush/linger behavior. No new licensing exception is inferred from metadata alone.

## Superseded multi-client integration proposal (history)

The native host currently keeps negotiation, sequence numbers, list cursors and a mutable settings borrow inside one private Session. A multi-client engine coordinator must preserve separate per-client protocol state while serializing access to the ONE EngineOwner/settings store. Client EOF must not call owner shutdown; explicit companion Quit must retire both directions, inspect cancellation failures and join runtime/engine work. Refresh defaults from owner settings rather than leaving other clients with a stale cached destination after a settings change.

Do not implement the output adapter by collecting an unbounded Vec or blocking the engine on a slow reader. Give incoming/outgoing queues explicit byte and frame budgets, reserve control-response capacity, and produce initial/overflow snapshot pages incrementally; synchronously enqueueing an entire history into a small queue can disconnect even a healthy client. Disconnecting a failed/slow client must not become an engine failure or automatically replay an uncertain Add. These actor/backpressure choices still require implementation and real-transport tests before pairing with native stdio/setup.

IPC now shares the established 1 MiB native body bound (LOCAL_IPC.md), while metadata/log bounds stay 64 KiB. The original IPC cap could not transparently support wire2; lowering the hello result would also fail the Firefox client's exact check. No installed binding was changed while resolving that contradiction.

## Selected first engine integration: one active controller

The multi-client coordinator above was a proposal, not a requirement. The first integrated bridge instead permits ONE active browser controller, preserving the released single-controller/state-lock behavior. Four transport reservations are a handshake bound, not a promise of four concurrent engine controllers. Additional connections stay outside protocol dispatch: one waiting peer can time out during authentication, and later opens may be refused immediately. No second engine is opened. Future multi-controller support would require the per-client/defaults/queue review above.

Refactor the existing private protocol session to await output one bounded frame at a time. Keep the legacy stdio entry point and its EOF shutdown semantics unchanged. For a local session, use a retained async reader with an eight-frame input queue (at most 8 MiB queued plus one reader-delivery body and one dispatched body: 10 MiB total input bodies); output has no extra queue, at most one encoded message plus the transport's buffered write. Initial/overflow snapshot pages are sent incrementally with bounded writes, retaining the existing snapshot ordering rather than interleaving deltas. Captured snapshot/list memory continues to scale with retained task history; the mailbox bound is not a claim about total process memory.

Local-session EOF/failure closes and joins its reader/writer scope, not the engine. The owner awaits session teardown, inspects cancellation failures, and resumes listening. Explicit Quit cancels the session through its stop signal, joins it, then checkpoints/joins the engine. Do not externally cancel a serving future and report a successful join. Slow output times out rather than indefinitely blocking controls; networking workers remain separately scheduled. No automatic command replay is added.


The initial implementation is opt-in through the native host crate's `local-bridge` feature, selected by the preview companion, not its legacy executable. `serve_local` retains one async reader in a JoinSet, closes both directions and awaits the reader before returning. Retirement failure is distinct from a bad/closed peer and is sticky at the companion worker; engine failures remain engine failures. Default stdio EOF still checkpoints/shuts down its legacy owner. Snapshot projection is now per page instead of a second whole-history description vector. Captured history, decoded command allocations and wrapper/kernel buffers are separate from the stated input-body budget.


## Selected next installed integration (not yet deployed)

Use one installed application image at the existing fixed helper leaf, with separate companion, native bridge and bounded fixture-probe entry modes. The companion remains a separate **process/lifetime**, not necessarily a separate executable file. This avoids claiming authority for a second executable absent from existing receipts: the installed helper SHA-256 binds both bridge and companion code. It does not bypass shortcut/lifecycle migration or persistent-XPI qualification. Setup retains independence from the application crates. Existing receipt/generation/file formats are not silently redefined; any additional shortcut ownership metadata needs explicit schema/migration tests.

Before opening state or connecting, verify the running image's fixed leaf/canonical generation path, current receipt, actual retained helper/XPI/manifest files, generated fixed-principal manifest and current registration. Hold metadata/file leases; take the existing cooperative setup lock only during inspection, without creating/adopting missing lock state. A matching record is content/installation binding, not publisher authenticity, engine ownership or proof of Firefox installation.

Create a fresh protected runtime directory for each engine session, bind the pipe before publishing discovery, and compare runtime record fields against the independently verified installation. Retain the real engine state lock for singleton authority. Stale/failed records are preserved, not treated as removal authority; discovery needs explicit enumeration/time limits. Transport capabilities may be stored only in the protected runtime record; HTTP session credentials remain memory-only. Neither capability possession nor discovery metadata permits uncertain Add replay.

Native stdio uses the exact retained I/O-only children described at the application checkpoint below, rather than global Tokio stdin, detached writers or a second raw cancellation exception. Pending output, partial/idle input and joins are exercised in owned tests; actual installed Firefox lifetime remains a separate gate.

Read-only review of Tokio1.53.1 `src/process/windows.rs` establishes that ChildStdio uses `Blocking<ArcFile>`, not the named-pipe async transport. AsHandle is not proof of overlapped cancellation. An I/O-only child design must prove that retiring the exact counterpart closes blocked parent reads/writes and that the blocking pool actually joins; no such adapter is implemented by the record component.


## Application/stdio integration checkpoint

The opt-in companion `installed` feature now builds `download-manager-app` with `--companion`, native bridge and two internal I/O-pump modes. The opt-in development package now selects it; production/installed qualification remains separate. The installed worker verifies the current image, opens the retained engine state lock, creates protected runtime publication, and only then acknowledges readiness. The existing confirmed-tray gate is shared with preview mode. Both modes use the same one-controller loop. Successful Quit requires session retirement, engine shutdown, publication removal and joined worker/runtime completion; failures preserve the domain.

Native bridge startup validates Firefox's fixed launch arguments and current image binding, considers bounded candidate hints within a five-second observation budget, and authenticates before consuming native input. Disk/ACL operations retain their separate limits and joined cleanup, not an unconditional five-second OS bound. Candidate attempts stop permanently when forwarding begins: disconnect never launches an engine or replays an uncertain command.

Two exact retained copies of the same verified image perform input/output framing only. Their arguments contain no endpoint/key/URL. Parent threads own bounded queues; the output pump acknowledges only after its actual stdout write/flush. Idle native input and stalled synchronous output are retired by closing the exact child counterparts (kill/wait), then joining the retained parent threads. No global Tokio stdin, detached blocking-pool I/O, new FFI cancellation exception, PID lookup or unowned process termination is used. Console capture is refused; inherited or explicitly owned redirected streams are required. Normal disconnect retains the companion engine.

Two actual-executable integration tests cover native stdio → authenticated pipe → one 64 KiB transfer, input EOF/reconnect with one task and independent bytes/Completed receipt, and a real 1 MiB output attempt to a nonreader while input is blocked on a partial prefix. The latter requires output failure, exact pump/thread retirement and observable output EOF. These use owned stdio/engine fixtures, not installed registration or Firefox. An initial byte read after filename appearance failed with Windows33 while promotion still held a lock; validation now separately observes durable Completed before reading bytes. The earlier failure is not relabelled as a pass.

Setup UI and paired development package/probe selection are implemented; shortcut ownership, actual installed registration and persistent Firefox capture qualification remain open. Preview reports and metadata fixtures must not be described as completion of those gates.

Parent-pipe-loss tests exposed two concrete gaps after the initial relay checkpoint: the output pump survived behind an unread consumer after its sole parent writer was killed, and the input pump survived private-parent-reader closure with native input held open. Both failed observations completed exact owned cleanup before asserting failure. Normal EOF tests had not proved these cases.

Input pumps now send a fixed zero byte every 250 ms through a separately drained private stderr pipe, never through native framing/log output. Loss of its sole parent reader retires that I/O-only process. Output pumps retain a private-input reader alongside synchronous output and enforce one outstanding frame until its actual write acknowledgement. EOF/malformed input while output is pending retires that process with failure, rather than leaving it blocked behind an external consumer.

Normal pump exit joins its internal monitor/reader thread. Parent-pipe failure can instead terminate the whole I/O-only process with status 1 while a synchronous worker is blocked: this is **process retirement, not cooperative thread join or successful delivery**. The retained parent/test still waits for actual process exit and joins its own threads. No native engine runs in these pump modes and no new FFI exception is used. Four real-executable relay tests now cover these cases. This establishes private-pipe lifetime behavior, not Firefox process-tree containment, installed workflow, or an unconditional scheduler/OS latency bound.
