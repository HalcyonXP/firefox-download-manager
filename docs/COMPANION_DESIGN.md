# Visible companion implementation — #50

Status: implementation in progress; not an installable successor release. This branch starts from accepted mainf944247 independently of #49/PR55. The exact owner-supplied Hugging Face URL and probe observations are recorded in #49/PR55; earlier unknown-provider wording is historical. The owner approved the user-facing infographic and said Proceed. That earlier checkpoint confirmed the direction only. The later explicit autonomous-completion instruction in [ADR0014](decisions/0014-autonomous-completion.md) now authorizes in-scope implementation, isolated tests and reviewed distribution without routine approvals; it does not supply credentials, waive operational preflights or request a Windows startup service. #49's browser/signing/handoff proof remains separate and open.

## Boundaries selected before implementation

- **Engine owner**: one Rust owner retains the existing TaskEngine state lock, settings and task lifetimes. Browser transport EOF is a client disconnect, not companion Quit. Existing on-demand run_host continues to shut down on EOF until the authenticated bridge is implemented and paired; do not silently detach the released host.
- **Visible shell**: Windows-native status window, tray icon, Open/status and deliberate Quit. First increment is an explicitly marked preview in an exclusively created temporary domain, never the installed state root. It does not pretend the Firefox bridge exists.
- **Visibility gate**: engine startup follows successful tray registration and confirmation. Failed registration leaves a visible error and no engine. Window close can hide only while the tray is confirmed. Quit requests cooperative engine shutdown, joins the retained worker, then removes the icon and exits. A failed shutdown must remain visible rather than report success.
- **Shell recovery**: confirm registration on an owned-window timer; re-add only this app's icon if confirmation fails. If re-add fails, show the status window. This is timer-driven recovery, not immediate TaskbarCreated notification or a guarantee against OS scheduling stalls. Test loss of the owned icon, not termination of Explorer. Windows tray overflow is not absence of registration.
- **IPC direction (transport foundation below; installed bridge still pending)**: bounded local Windows named pipes, explicit current-user ACL and remote-client refusal, random per-generation/session capability, paired bridge/companion version, independently checked generation authority, bounded clients/queues/deadlines and deterministic refusal of unknown installations. No HTTP listener or URL/secrets in process arguments. Current-user confinement does not defend against administrator or arbitrary code already running as that user. Credentials and sensitive URLs must stay out of ordinary logs.
- **Protocol direction**: v2 manual task controls remain the compatibility baseline; automatic handoff needs a separately versioned prepared/committed intent contract established with #49/#51. A lost Add acknowledgement must not trigger an automatic replay. No browser profile or registered host is repointed to a partial implementation.
- **Setup migration direction**: a future paired package adds the companion and an ordinary setup UI/owned shortcut, migrates only verified receipts/generations, closes both Firefox editions normally before registration changes and preserves downloads/task state/unknown files. Existing generation manifests are not edited in place. Preview bytes are excluded from the current package payload list; no v0.1.0 tag/asset is replaced.

## Dependency choice and rejected shortcuts

winsafe0.0.29 is selected for safe native-window and Shell_NotifyIcon wrappers, features gui/shell only, no default features, no transitive dependencies or build script. Its full MIT license, package manifest and relevant API wrappers were reviewed before incorporation. At the initial shell checkpoint first-party unsafe_code remained forbidden. [ADR0015](decisions/0015-owned-windows-io-cancellation.md) now adds one explicit function-local cancellation exception in a separate Windows I/O boundary; the shell and all existing crates retain forbid. No third-party implementation source is copied.

A direct TaskbarCreated handler through winsafe would require unsafe conversion from its registered u32 message ID to its typed WM; this was not used or bypassed. The chosen adapter instead uses the predefined WM_APP for its owned icon callback and a timer for confirmation/re-registration. No raw Win32 FFI is needed for those UI operations; no Windows message-filter/protection change is made. The separate IPC cancellation boundary is addressed by ADR0015.

tray-icon0.24.2 was reviewed but not selected: its constructor can retain a window after failed icon registration (build success alone is not visibility), and the selected design does not need its extra menu/platform dependency tree or message-filter adjustments. native-windows-gui1.0.13 was considered but not selected. interprocess2.4.4 was initially only an IPC candidate. The subsequent [local transport increment](LOCAL_IPC.md) selects its server/security-descriptor APIs, not its client constructor or default flush/linger behavior. No new licensing exception is inferred from metadata alone.

## Required evidence still ahead

Pure lifecycle tests, actual owned TaskEngine lifetime/lock/checkpoint tests, native window/tray interaction and owned-icon-loss recovery are distinct layers. `EngineOwner` now separates state/settings lifetime from a borrowed protocol session; existing `run_host` still shuts down on EOF. `crates/companion` adds the retained worker and safe Windows preview shell. The preview intentionally allows distinct isolated domains, not a proven installed per-user singleton or IPC connection. The first increment must preserve that distinction. It cannot close #50 without real singleton/IPC/reconnect/quit and installer lifecycle acceptance. Actual Firefox/setup qualification is now authorized under ADR0014, subject to ownership and closed-app preflights. Signing, real ordinary-click capture and final exact-artifact publication remain #49/#51–#53 gates.


## First increment evidence and limits

- Three lifecycle tests enforce confirmed visibility before startup, no duplicate start after icon recovery, sticky Quit, completed-join acknowledgement and visible failure. Removing the visibility condition or making Quit immediately Stopped failed the intended assertions; restored tests passed.
- Three owned engine tests cover an in-process observer going away while the real transfer completes with exact fixture bytes, an exclusive lock retained through shutdown acknowledgement, paused/checkpointed zero-prefix transfer recovery, and early Quit of the retained runtime worker. These are not browser reconnect or nonzero-prefix crash proofs. Existing native-host EOF, settings, privacy and compiled-host crash tests still pass after the owner/settings-borrow refactor.
- Initial native-Windows preview runs passed six checks: real status window/engine readiness and tray registration, Hide preserving registration, a synthetic owned tray callback opening status, acknowledged deletion/re-registration of only the owned icon, Quit/process join/icon absence, and state-lock release with no downloaded files. These use native button messages and an owned callback, not physical mouse/keyboard input or real Explorer restart. Reports stay under ignored artifacts with their own binary/harness identities.
- A native adapter mutation suppressing re-ADD failed specifically at owned-icon recovery and published no success report. It was restored and the six-check run passed. The early failure driver did not record which containment path it used; do not reconstruct that fact. The current driver additionally records retained-handle termination/join outcomes privately on failure, and checks native AMD64 process identity. Earlier reports retain their narrower metadata.
- A successful rectangle lookup alone is not recovery proof: the driver requires the visible acknowledgement counter to advance after deleting the owned icon, then verifies its rectangle. It does not require sampling a fleeting absence or add a sleep to make a timing assumption pass.
- Early compile/lint feedback corrected a WString menu API mismatch, lifetime elision, checked message-number conversion and an equivalent let-chain. No lint, visibility, join or recovery predicate was weakened.

The Windows preview uses inherited workspace0.1.0 development versioning but is not part of released v0.1.0. Initial UI evidence used development builds and a dirty working tree; source/binary changes require fresh reports, not reuse as exact-input evidence. Full workspace tests, Clippy, dependency policy and authoritative PR CI remain gates on the increment; passing them does not complete #50.

## Maintainer-only preview

Build the companion with Cargo, then run `scripts/test-companion-preview.py --report artifacts/<new-name>.json` on the owned interactive Windows11x64 machine. The driver launches only the fixed target/debug companion with `--preview`, gives it a fresh temporary parent, checks only that retained process's windows/icon and joins it before publishing a bounded report. No installed Firefox/native-host registry binding is read or changed. It does not launch/restart/close Firefox or touch its profiles. Private preview state is deliberately retained, not adopted later or recursively swept.

Manual `--preview` also uses a newly created temporary state domain. No-argument execution refuses with an explanatory window and opens no installed state. This is a maintainer preview, not a user install command. Do not add these commands to the five-step user quick start or repoint a native manifest to this unfinished binary. Real user tray/keyboard/menu interaction, IPC authentication/singleton/backpressure, real browser restart and ordinary installer/shortcut/upgrade/removal qualification still remain.
