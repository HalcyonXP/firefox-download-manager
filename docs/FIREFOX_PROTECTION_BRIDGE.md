# Firefox download-protection bridge

## Scope and current state

Native transfer ownership remains in the companion. Public automatic capture remains disabled pending protection integration. Windows Internet-zone metadata is provenance, not a Firefox reputation result. The default/manual and capture-candidate manifests do **not** select a privileged API.

`extension/protection-probe/` is the first, separately built **fileless service probe**, not the production bridge. A Firefox **API experiment** is privileged browser-parent code registered through `experiment_apis`; here it exposes only `managerProtection.start()` and `snapshot()`, both without arguments. This additional trust boundary is not general-purpose access to files, profiles, preferences, arbitrary URLs or commands.

The source is restricted to one exact, non-private, top-level extension tab (`probe.html`) and one retained caller context. Content scripts, frames, background pages, other extensions, query/fragment variants and replacement contexts refuse. One attempt is consumed before service construction/dispatch; repeated calls only observe the same attempt. Closing the context/extension revokes observation. The service has no cancellation handle: context closure is **not** service retirement; the owned Firefox process must exit and be joined.

## Fixed query and interpretation

The only query describes an empty unsigned text fixture at a fixed HTTP127.0.0.1 URL. Its zero length, empty-content SHA-256 and empty signature array are constructed inside the privileged component. The current receipt-v2 probe additionally constructs one fixed `nsIRedirectHistoryEntry` backed by a native default-context loopback principal, plus native `nsIReferrerInfo` holding a fixed original loopback referrer with sending disabled. These are synthetic fixture values, not captured browser history. No caller supplies these fields. No file is opened, downloaded, scanned or published by this probe; it does not issue an HTTP request to that fixture URL. Firefox's existing protection service remains responsible for any normal protection-provider activity.

The direct service callback is classified using its boolean, status and known verdict range. Errors, malformed/contradictory results, uncertain throws and duplicate callbacks produce `unavailable`; callback counts saturate at two. A successful nonblocking policy result is called **not-blocked**, not “safe.” Receipts contain only fixed classifications/counts and always `qualification:false`. Polling is bounded and never reissues the query. A pending/failed observation is not a successful probe.

Receipt-v2 adds a bounded `metadata_reads` bit mask: source URI1, referrer-info2, history-entry principal4, suggested filename8, unexpected history-field access16. Acceptance requires exactly15 before the one successful callback. Missing consumption or access to unsupported history fields produces `unavailable`, even if the service normalizes its own error. These witnesses establish getter access, not successful internal URL classifications, actual request provenance or real-file safety. Node models cover every omitted expected getter and ignored unexpected-access errors. The nonempty-context variant was observed at cleane1a982f with mask15 and one successful callback, as scoped below. The earlier v1 result used empty redirects and a null referrer.

The owned driver first checks refusal from a query-bearing page, then the fixed query and unchanged receipt after a repeated start, then refusal after caller-context retirement. Initial page text is `starting`, distinct from refusal, so a script that never ran cannot satisfy a negative case.

## Verified source distinctions

Reviewed Firefox source identifies these consequential boundaries:

- `DownloadIntegration.shouldBlockForReputationCheck` can resolve nonblocking when saver hash/signature extraction fails; it also normalizes callback outcomes without exposing the callback status. The probe therefore calls the service directly and checks its status, rather than interpreting that convenience result as successful checking.
- `ApplicationReputation.cpp` checks source/redirect/referrer URL blocklists before its non-binary completion path. A `.gguf`-only policy does not by itself remove this requirement. Internal Firefox fallback behavior still belongs to that service; observing `not-blocked` does not prove every underlying check succeeded.
- `nsIApplicationReputationQuery` takes a raw-byte SHA-256 string, three levels of byte arrays for certificate-chain signature information, and an `nsIArray` of redirects. The IDL comment calls the elements principals, but the implementation queries each element as `nsIRedirectHistoryEntry` and then obtains its principal; direct principal elements are not the implemented contract. Its `fileSize` is currently a 32-bit unsigned long, consumed when constructing a remote request: large-file behavior must be reviewed before provider qualification. The probe's size is zero; it does not qualify large files.
- `DoLookupInternal` uses the original referrer before policy reduction, not merely the sent `Referer` header. It also ignores the return from `AddRedirects`; a successful callback alone cannot prove all redirect entries were consumed. A real adapter must provide valid history entries and reject failed/missing expected metadata consumption independently. The older empty-history observation does not cover this boundary.
- Experiment availability, privileged status and persistent installation are separate. The experiment preference's source fallback is not an observation of effective profile settings. Temporary loading does not qualify ordinary persistent installation.
- Windows `DownloadIntegration.downloadDone` writes origin metadata separately and explicitly avoids `IAttachmentExecute.Save`; calling that entire completion routine would also perform unrelated permissions/notification operations. It is not a narrowly scoped substitute for a reputation query.

Source reference: Mozilla revision [`574c275bcf5b4f86198c979b7e61f4a844aba0ea`](https://hg.mozilla.org/releases/mozilla-beta/file/574c275bcf5b4f86198c979b7e61f4a844aba0ea/), particularly `toolkit/components/reputationservice/nsIApplicationReputation.idl`, `ApplicationReputation.cpp`, `netwerk/base/nsIRedirectHistoryEntry.idl`, `dom/interfaces/security/nsIReferrerInfo.idl`, `dom/chrome-webidl/ChannelWrapper.webidl`, `netwerk/base/nsILoadInfo.idl`, `caps/nsIPrincipal.idl`, `WebRequest.sys.mjs`/`ext-webRequest.js`, `nsExternalHelperAppService.cpp`, `DownloadLegacy.sys.mjs`, the installed `DownloadIntegration.sys.mjs`, `toolkit/components/extensions/Extension{,Parent}.sys.mjs` and `toolkit/mozapps/extensions/internal/AddonSettings.sys.mjs`. No vendor source is redistributed by the probe.

### Durable requirement and restart

Protected handoffs use closed envelope6: ordinary task4 fields, required handoff phase and exact `protection:"browser-bound-v1"`. Missing/null/false/unknown protection values, extra fields, sessions and conflicting native final URLs refuse. Older readers cannot mistake envelope6 for an unprotected task. Only the immutable requirement is new persisted information. Browser source/referrer/history/principals, fingerprints, decisions, request IDs and receiver lifetimes are **not** added to disk. Recovered protected tasks cannot execute through commit/start/retry/resume, even with a new receiver or identical repeated preparation. ### Native bytes and one-use publication

The common protected probe/reprobe path selects anonymous no-redirect probing, including explicit retries; transfer requests already refuse redirects. Persisted protected resource identity must retain the same native URL. Starting from the captured final browser URL can therefore enforce empty **native** history, but does not supply the preceding **browser** history. See [HTTP.md](HTTP.md#opt-in-anonymous-no-redirect-probe).

Protected completion always computes the full64-bit length and SHA-256 under the existing validation lease and applies any expected checksum before requesting a decision. `NamedValidatedPartial` freezes index0 of the original sanitized filename and retains that lease throughout the wait. A native-origin `ProtectionRequest` exposes only its fresh UUID, handoff ID, run generation, receiver-lifetime UUID, source URL, exact filename and computed fingerprint. It is noncloneable, nonserializable and redacts Debug output; no caller supplies byte identity. The single consuming `decide` route cannot be replayed onto another attempt. Its success means a response was queued, **not** that output was published or transport delivery occurred.

At most32 outstanding authorizations are retained, including requests already taken by the adapter and approved owners not yet consumed. Queue/capacity exhaustion, dropped request, unavailable/blocked decision, closed receiver or cancellation fails closed. Explicit retry recomputes identity and requires a new request/generation/decision. The final owner rechecks cancellation, receiver liveness and publication-lock integrity, then enters the existing Promoting checkpoint and attempts exactly one exclusive name. A late collision returns FileExists without numbering or overwriting. Receiver closure and this short synchronous checkpoint/publication section share a lock: an already-entered publication precedes close; a close that wins prevents publication. No lock is held while awaiting a service, transferring or hashing. A poisoned publication owner cannot authorize reuse.

Closure wakes pending protection waits and refuses future probes/publication, but is **not** automatic cancellation of an already-running HTTP transfer, a service deadline or a process join. A future adapter must stop owned work when appropriate and retain/join all engine/transport/process owners. A live adapter that never replies leaves a bounded, cancellable unpublished task; no timeout is interpreted as permission. Browser-context retirement still needs explicit trusted-adapter revocation. The engine cannot validate a dishonest/misbound policy implementation supplied by native code.

The engine distinguishes ProtectionBlocked/ProtectionUnavailable internally. No new closed wire enum or capability is advertised; the existing host conservatively maps these unselected conditions to INTERNAL_ERROR. Specific wire/UI projection requires separately negotiated integration rather than silently extending strict validators.

## Parent transport admission (opt-in, capture disabled)

`EngineOwner::serve_parent_transport` is a separate local-bridge library entry. It refuses ordinary-class channels before I/O; `serve_local` continues to refuse parent-class channels. The new method takes the same exclusive mutable engine-owner borrow and reuses retained reader retirement; it does not open another engine or transfer engine lifetime to the connection.

Before wire2, the native side emits a closed offer with `parent_transport:1`, a fresh native-generated UUIDv4 `admission_id`, `kind:"offer"` and `capture_ready:false`. A queued offer/accept write is not a received ready frame; the ID correlates one connection, not Firefox authentication, a captured request, an engine protection lifetime or a browser-context epoch.

## Production integration still required

Before public capture can be enabled, the bridge must bind an independently validated native partial and its final filename/hash/signatures to the actual browser source/referrer/redirect history and any native redirect changes. There must be no caller-chosen path or general scanning endpoint. Missing/stale context, broker loss/restart, service uncertainty or unsupported policy must prevent final publication; a verdict must not be replayable onto another task or changed bytes. Existing file leases, immutable handoff IDs, cancellation proof and exclusive final promotion remain authoritative.

Reputation is not the only applicable download check. Matching Firefox source also applies automatic-download permission/spam handling and `ClassifyDownload` before transfer, parental-controls checks, and active content-analysis policy. A trusted click or nonblocking reputation callback does not replace those checks. The initial bridge must either honor applicable policy or leave such cases Firefox-owned; it must not disable policy or invoke a whole handler with unrelated cancellation, permission-writing, credential-copying or file side effects just to obtain metadata. The metadata reader above performs none of these policy decisions.

The fileless probe implements none of the native gate above. Actual browser/native-context binding, policy execution, large-file semantics and same-byte/provider acceptance remain unimplemented; the native component deliberately refuses recovered protected execution instead of persisting sensitive browser context. Public capture, persistent unsigned installation and final paired release remain open in [PROJECT_PLAN.md](PROJECT_PLAN.md).
