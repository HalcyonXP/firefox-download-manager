# Companion shortcut ownership migration

## Implemented development boundary (installed launch qualification pending)

Receipt1/journal1 remain the legacy three-file-generation format. The paired application setup uses receipt2/journal2: current generation owns an additional `Download Manager.lnk` and its SHA-256; receipt2 binds the independently supplied canonical Programs directory by SHA-256. These are installation schemas, not wire/task/settings versions. Receipt1 cannot authorize a shortcut, and a legacy session without a matching Programs context refuses receipt2 mutation/recovery.

The ordinary launch entry is `Programs/Download Manager <installation UUID>/Download Manager.lnk`. Production obtains current-user Programs from Windows, not a persisted path. Tests supply an independently created Programs fixture. No desktop, Startup folder, service, elevation, browser profile or logon behavior is added. Redirected/unsafe/nonlocal directories are refused by existing directory leases, not repaired.

A first paired install or receipt1 upgrade exclusively creates the per-installation folder before journaling; a pre-existing folder is not adopted. A crash before the ownership journal preserves that orphan. Upgrades bind the same Programs scope and validate the previous link. The generation copy is immutable and contains the exact bytes used for activation/rollback. The native Shell Link API serializes to memory; Rust performs exclusive file creation and checked replacement, never `IPersistFile::Save` to a pre-existing path. Link readback uses raw target/arguments without Resolve, shell execution or distributed tracking.

Journal2 install recovery validates the previous paired generation even when its registration was absent, and restores only the previous owned link or removes the new matching link; uninstall removes matching link bytes before removing the generation copy. Missing links are tolerated during removal, unknown/changed links refuse success. Cleanup preserves the current entry and removes only known retired generation copies. Empty-folder removal is nonrecursive; unknown entries survive. Registration, receipt, link publication, process creation and tray readiness remain distinct observations.

Receipt transitions are monotonic (1→1, 1→2, 2→2), with stable scope for 2→2. New optional fields must be absent in legacy records, not null. Schema tests cover missing/duplicate/null/future fields, version/scope mismatch and monotonic edges. Real Windows filesystem/COM tests cover legacy migration, fresh paired installation, upgrade, cleanup, uninstall, locked images/links, changed links, scope refusal, unowned folder refusal and interrupted activation/removal. An installed launch and actual Start Menu interaction still need separate qualification; COM readback and memory-registration tests do not supply it.

## Verification limits and retained observations

The actual application participates in a receipt2 installation/repair/upgrade/cleanup/uninstall fixture with memory-only registration and synthetic XPI bytes. A separate installed-image metadata fixture retains the additional immutable link and rejects another target or elevation flag even when the recorded digest is updated to match. The header allows only local target-list/info, description, working directory, arguments and Unicode flags; expansion, elevation, Darwin and shim modes are refused before COM decoding. Native Shell Link bytes contain local target metadata and are created at installation, never included as package/publication inputs. No signing, account isolation or publisher authority is inferred from content agreement.

The first independent target comparison failed because the fixture retained an 8.3 temporary-directory spelling while Windows/installation paths were canonical long names. That failed fixture is preserved; the comparison now uses the independently canonical session root rather than weakening target equality. A failed migration-folder collision can leave a new empty generation directory before a journal exists; it is preserved, not adopted or retrospectively journaled. Registration repair currently requires an intact matching shortcut; it does not silently rebuild missing/changed entries. Missing entries are tolerated only for conservative uninstall/recovery.

The Windows wrapper/API surface and stock `shlwapi.dll` import are reviewed in THIRD_PARTY.md. Setup changes only its exclusively created per-installation Programs folder; no normal Start Menu or shared registry mutation is part of the available fixture evidence. Raw-target readback is not actual Shell launch, taskbar pinning behavior or a physical Start Menu click. Actual installed GUI-to-tray/bridge and browser/XPI acceptance remain open.

### Paired entry compatibility change

Application entry family1 (the prior development candidate) reads only receipt1. Setup must not accept that metadata response and then publish receipt2 it cannot open. The probe envelope remains format1, but `entry_modes_version` now explicitly advances to2 in both producer and verifier. Family1 is refused before activation; native wire2 and package-version matching are unchanged. This requires a newly paired helper/setup build, not reuse of the previous development helper with the new installer.

The packaged family2 helper is accepted by the packaged setup probe; the actual earlier family1 helper and actual legacy native host are refused in fresh owned domains with joined process observation. These negative domains are preserved. All eight development payload digests independently match their descriptor; actual PE imports select only `SHCreateMemStream` from the newly reviewed stock `shlwapi.dll`.
