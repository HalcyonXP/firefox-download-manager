# Protected runtime-record primitive

Status: an opt-in Windows component in setup's `private-file` feature. No installed caller selects it yet. It is **not** installed bridge, singleton, generation, native forwarding or Firefox qualification. The default setup package does not select this feature.

## Purpose and authority limits

A future companion must publish its endpoint/capability without exposing a secret before permissions are established. `PublishedFile::create` and `PrivateFile::open` provide one fixed `companion-runtime.json` file, not its eventual record schema. Contents must be 1–4096 bytes. The caller must independently establish directory ownership and installation/receipt authority; `DirectoryLease` alone establishes neither.

The supplied directory must already have a **protected DACL** (discretionary access-control list), a current-user/SYSTEM/Administrators owner, and no other unprivileged principal able to mutate it or its children. Protection prevents later ancestor inheritance from reopening the namespace. The adapter does not seal, repair or adopt a supplied directory. Preparation of the installed private directory remains unfinished.

Only ordinary allow/deny ACEs (access-control entries) are accepted in the parent. Inherit-only ACEs do not apply to that directory. Allow masks for other principals must exclude generic all/write, delete, change-DACL/owner, add-file/subdirectory, write-EA/attributes and delete-child rights (`0x500d0156`). Other read permissions are not secret-file permissions: the file gets its own protected descriptor with no inheritance.

Same-user arbitrary code, Administrators and SYSTEM are outside this confidentiality boundary. Actual cross-account/restricted-token behavior remains unqualified. No new account, privilege adjustment or service is involved. No claim is made about secure erasure or encrypted storage.

## Creation, readback and leases

1. Retain canonical ordinary-directory ancestors against rename/deletion. Reject ambiguous, nonlocal and reparse paths using existing setup confinement.
2. Resolve Windows PowerShell through `GetSystemDirectory`, never PATH or an environment-supplied executable. Run a fixed embedded script with `-NoProfile -NonInteractive` and `CREATE_NO_WINDOW`. No execution-policy setting, profile, registry, network call, external child command, custom P/Invoke or dynamically compiled interop is used.
3. A fixed bootstrap first constructs a dedicated strict UTF-8 reader over raw stdin, emits `start` and flushes stdout. Rust must validate that marker **before writing a request**; process creation alone is not script initialization. `start` proves neither permissions nor publication. The auxiliary process then receives **only a whitelisted opcode and literal path as two UTF-8 lines over stdin**, validates them and flushes `input` before permission work. This request receipt is distinct from file readiness. It derives the current per-user SID from its Windows identity. No contents, key, hex/base64 payload or supplied path is placed in command-line arguments. Secret contents never enter PowerShell, including its parameter logging.
4. After checking the parent, .NET `FileStream` creates a new empty file with the protected current-user-only full-control descriptor **in the OS creation operation**. Existing entries are refused, never truncated or adopted. The child retains read/write access and denies deletion.
5. Actual owner/DACL readback must find precisely the current user as owner, a protected DACL and one non-inherited/non-inheritable allow ACE granting that user exact file full control. Null/broad/other-principal/unprotected descriptors are refused.
6. The child sends `ready`; this means a retained empty protected file, **not a published record or an engine ready signal**. Rust opens that same non-reparse file for writing while the creator's handle prevents replacement. A second auxiliary invocation independently checks actual permissions before Rust writes anything. Rust writes and calls `sync_all`; the auxiliary process never reads or writes those contents.
7. Rust drops its writer, sends `close`, observes the child's exact `ok` receipt and successful process exit, and joins its I/O worker. A normal `PrivateFile` reader denies shared writes, so it cannot open the record while the creator/writer remains active. File-name presence is not readable publication.
8. The publisher reopens a read-only, no-write/no-delete lease, independently verifies actual permissions again **before reading**, and compares the complete bounded contents to the original bytes. Readers use the same pre-read checks. Only successful create-new publication yields the removal-capable wrapper; read-only opening does not authorize removal or adoption.

The parent and file leases remain with the returned object. Removal closes the publisher's read handle while retaining ancestors and removes only its fixed file; competing readers cause refusal. No recursive directory cleanup or stale-record recovery is provided. Failed, empty or partially written creations remain for separately owned recovery; an error never authorizes replacement.

## Auxiliary-process boundary

Input is at most 2 KiB: one whitelisted opcode line and one control-free, drive-qualified path line, each LF-terminated. Rust applies existing lexical confinement before encoding; the helper validates opcode/path shape and does not enable BOM-based encoding detection. Startup, request-consumed and readiness are separate exact six-byte markers; completion is exactly two bytes, with a one-byte excess detector. Diagnostics are fixed; OS exceptions are not echoed. A retained worker handles potentially blocking stdin/stdout. The five-second per-adapter deadline bounds waiting for helper work, not an unconditional bound on filesystem I/O or joined cleanup. Early errors close the coordination channel, retire only the exact retained child handle and join the worker. Process exit, receipt validity and worker join are separate checks. A blocked or constrained Windows PowerShell environment refuses operation; protections are not changed to obtain success.

This reuses the already reviewed winsafe system-directory API and Windows-supplied .NET file/security classes, not a new Rust FFI exception or a new registry dependency. The feature does not alter ADR0015.

## Exclusive protected-directory preparation

The opt-in `private-directory` feature creates `companion-runtime` below an independently owned, leased parent. It verifies ancestor namespace permissions, calls winsafe0.0.29's synchronous CreateDirectory with an explicit current-user owner and protected **current-user read-only bootstrap DACL**, retains an ordinary DirectoryLease, then independently verifies the initial descriptor before granting and reading back user-only inheritable full control. Existing entries are refused by the create operation, never adopted or repaired. Failure preserves newly created directories. Only a successful creator receives empty-directory removal authority; other leases/nonempty directories refuse removal. File publication still uses the separate atomic protected-file creator. No installed caller or receipt/generation/engine authority is implied.

### SDK and namespace review

The additional winsafe advapi surfaces are ConvertStringSidToSid (LocalFree-owned SID) and InitializeSecurityDescriptor; CreateDirectory is a kernel wrapper. The repr(C) read ACL is 44 bytes: an 8-byte revision2 ACL header, a 36-byte ordinary allowed ACE with zero flags and FILE_GENERIC_READ (0x120089), then the canonical five-subauthority current SID. Offset tests check the header, ACE, mask and SID alignment. The ACL pointer is derived from the **whole allocation**, not just its eight-byte header field; Windows reads all AclSize bytes. It and the SID guard remain live throughout the synchronous copy. The owner const-to-mut pointer cast is an SDK read-only input, not a fabricated mutable reference or ownership transfer. SECURITY_ATTRIBUTES retains the descriptor borrow. No new first-party unsafe block, helper-language interop or registry package is selected. Cargo.lock adds only setup's optional first-party local-ipc dependency; the existing bounded joined identity adapter exposes opaque CurrentUser observations, not authority.

The parent/ancestor check rejects unknown owners, null/unsupported DACLs, effective other-principal descriptor/owner/attribute mutation, FILE_WRITE_DATA (potential reparse-control access), and immediate-parent FILE_DELETE_CHILD. Adding sibling directories alone cannot replace an exclusive creation. All ancestors stay leased and at least one protected ancestor is required. The exact Windows Modules Installer (TrustedInstaller) service SID is accepted only in the privileged ancestor policy, alongside current user/SYSTEM/Administrators; arbitrary service SIDs and non-current owners of the new directory are not accepted. No ancestor permissions are changed.

## Opt-in installed-image and runtime-record composition

`installed-runtime` adds a retained InstalledImage inspection and closed runtime-record format1. The selected next deployment uses one installed application image for companion and bridge roles, so the existing helper digest covers both; the application entry modes/paired package are **not yet implemented or selected**. See COMPANION_DESIGN.md. Existing receipt1/generation fields and native wire2/IPC1 are unchanged.

InstalledImage's public entry accepts no executable or root from a native message: it derives the running fixed helper leaf, requires a canonical current generation under local application data, and takes the **existing** cooperative setup lock only during inspection. A missing lock is refused, not created. It retains the receipt, helper, XPI and generated fixed-principal manifest files against write/deletion, verifies actual hashes and exact current registration, and refuses transaction journals/incompatible versions. The record binding includes installation UUID, current generation UUID, package version, helper SHA-256 and the SHA-256 of the actual receipt bytes. This is content/installation binding, not publisher authenticity, engine ownership or XPI signing/installation proof.

RuntimePublication borrows the verified image and privately owns a freshly bound Server, exposing it only after complete successful file publication. A prepublication review replaced the borrowed-server prototype because it could allow concurrent acceptance before a failed publication completed. The factory closes its unexposed listener on failure; it cannot be used to serve from that failed publisher. It creates `companion-runtime.<endpoint UUIDv4>` exclusively, then the fixed `companion-runtime.json` private file; runtime filenames are derived from typed canonical endpoints, never arbitrary caller paths. Child-record path length is checked before creating the directory. Known transport cancellation failure refuses removal. The caller must still retain the real engine state lock and join session/engine work before removal. Existing and failed domains are preserved. No production caller selects this component yet.

The closed JSON has format `firefox-download-manager-runtime`, version1, ipc_version1, protocol_version2, the binding object above, endpoint and exactly64 lowercase hexadecimal capability characters. Unknown/duplicate/missing fields and mismatching binding/endpoint/version fail closed; maximum4096 bytes, including trailing whitespace. Capability storage is a deliberate change from memory-only preview transport keys, **not** permission to persist HTTP cookies/Authorization or download-session credentials. Secrets remain inside Rust and the independently verified protected file, never PowerShell/process arguments/ordinary logs; no secure-erasure claim is made.

RuntimeConnection derives the directory below its verified image root, opens/verifies private file permissions before reading, then compares the closed record to independently inspected metadata. `candidates()` inspects at most64 total install-root entries, preserves unknown non-session files and refuses malformed session names/excess entries. A candidate is only a hint; authentication, engine ownership and liveness are separate. This bounds enumeration count, not aggregate disk/ACL-adapter time. A complete native discovery/timeout/reconnect policy and stale-domain lifecycle are still required; no record is silently adopted, deleted or replayed.
