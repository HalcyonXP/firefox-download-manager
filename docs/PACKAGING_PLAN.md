# Packaging implementation and evidence — #27

Baseline: security-reviewed `0a81007`; #26 findings remain binding. **Setup/package implementation and actual public installation CI have passed. Final #28 qualification remains pending; no qualified release is published.** User-facing commands: [INSTALLATION.md](INSTALLATION.md).

## Implemented decisions

- Separate Rust setup executable, not an execution-policy-bypassing installer. The old PowerShell registration/test scripts are now refusal-only retirement stubs; static guards prevent their use as an unsafe fallback. `winreg` 0.56.0 (MIT, optional features disabled) was deliberately reviewed before incorporation.
- Current-user registration only, fixed 64-bit HKCU key and exact extension identity. No service, elevation, firewall/route/VPN changes, telemetry, remote update or browser-profile editing. Mutating commands refuse running Firefox/helpers; only a setup-owned probe child may be terminated.
- Ordinary non-reparse, canonical drive-qualified roots beneath local application data, disjoint from task state. Directory ancestor leases narrow ordinary rename/reparse races. Root cap: 160 UTF-16 units; directory cap: 240. UNC/device/traversal/ambiguous spellings fail closed.
- A persistent zero-byte `setup.lock` serializes cooperating setup processes in one application-data domain. Production uses the normal current-user environment; isolated tests deliberately override it. This is not a global kernel mutex across arbitrary environment overrides or a hostile-account security boundary.
- Immutable UUID generation directories contain only the helper, XPI and exact generated manifest. A closed 64-KiB receipt records at most four generations and their hashes. Unknown files are never swept; verified retired files are removed explicitly with `cleanup`.
- The generation directory is created exclusively **before** its journal can claim it. A name collision cannot become rollback authority. Create-new bounded copy, copied-byte hashes, isolated helper hello and a final hash recheck precede registration activation. A crash before journal creation can leave an unrecorded directory for explicit inspection, not guessed cleanup.
- `recover` rolls interrupted installation back to proven prior registration/receipt, or finishes journaled cleanup/removal. `repair` separately rebinds a verified current generation only when registration is absent or belongs to a generation in the same receipt. Torn/changed bytes and foreign registry changes are preserved/refused.
- Registry rechecks are not atomic CAS against noncooperating account actors. Synchronized files and registry hive persistence are not one power-loss transaction. A registry flush call was investigated but is not exposed by the chosen safe adapter; no durability claim relies on it.
- Setup preserves state bytes and completed downloads. The helper performs supported v1/v2/v3-to-v4 task migrations at normal startup. Same-version upgrade is tested honestly: no earlier qualified product release exists. Temporary unsigned XPIs require explicit reload after each Firefox restart; setup never edits a profile or signing preference.

## Artifact recipe and licensing decision history

The paired version remains **0.1.0 / wire 2 / task state 4 / settings 2 / minimum Firefox 156**. Fixed payloads: helper/setup EXEs, unsigned XPI, installation/security instructions, third-party notices and build information. A bounded descriptor hashes those leaves; inner checksums and a separate ZIP checksum avoid self-reference. Only allowlisted inputs are copied—no checkout history, raw state/profiles, test-server executable, toolchain archive or private audit inputs.

The initial static MSVC prototype passed local build/PE-import/probe checks. Reading the actual Visual Studio 2026 Community distributable-code terms then exposed distributor/external-end-user requirements beyond notices alone. That recipe was **not selected for binary distribution**; no public binary was uploaded. This is a project packaging decision, not a general legal finding about MSVC projects or a newly confirmed user preference.

The replacement recipe uses Rust **1.93.1**, target **`x86_64-pc-windows-gnullvm`**, and SHA-256-pinned **LLVM/MinGW 20260826 UCRT x64**. LLVM/MinGW support is static; UCRT/Windows API DLLs come from Windows 11. No separate VC redistributable or bundled Microsoft runtime is required. `link-self-contained=no` selects the reviewed external runtime. [THIRD_PARTY.md](THIRD_PARTY.md) records LLVM exceptions, MinGW licensing and selected-object review; unknown runtime objects/imports require review before packaging. No first-party license was selected.

`build-package.ps1` prepares/verifies the build-only toolchain beneath ignored `target`, uses locked dependencies and explicit targets, remaps Rust/C paths and disables linker timestamps. It can run the full release-target test suite. ZIP order/timestamps are deterministic; binary bit reproducibility requires actual repeated-build comparison, not confidence in flags. `BUILD-INFO.json` records source commit, dirty/development status, actual tool versions, dependency inventory, runtime objects and PE imports. Hash consistency is not publisher authentication or proof of asserted source origin. CI candidates are not qualified GitHub releases.

These are candidate measurements, not released artifact identities.

Local versus CI binaries also differed. Cross-environment bit reproducibility is **not established**; no single cause has been proved. Package metadata already records compiler/Node/Python/zlib versions and now also npm/CMake/Ninja. A known text-input variation was corrected: Git-clean CRLF working files are normalized to LF for packaged instructions, matching the repository's existing `.gitattributes`. That correction does not explain away the binary difference.

The first lifecycle reports called the descriptor hash `package_sha256`; it meant SHA-256 of `package.json`, **not the ZIP**. New reports use the unambiguous `descriptor_sha256`. The ZIP digest remains in `PACKAGE-SHA256SUMS.txt`.
